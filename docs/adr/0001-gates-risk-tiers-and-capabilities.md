# Presets answer three questions apart: gate, risk tier and capability

## Context and Problem Statement

Each profile (`profile-app`, `profile-site`, `profile-library`, `profile-image-set`) answered three
independent questions at once:

1. **Gate.** May green CI merge a third-party minor, patch or pin update, or must a person merge it?
   This is a property of the repository: does what merges ship, or do consumers take each release
   through a pull request of their own?
2. **Risk.** Some dependencies never ship (linters, formatters, test runners, type packages), and
   some deserve a person whatever the repository (token and OIDC libraries, database drivers).
   This is a property of the dependency.
3. **Capability.** What Renovate has to detect: Go modules, Dockerfile `ARG` pins, agent packages
   in `apm.yml`, GitOps manifests. This is a property of the files in the repository.

Mixing them had visible costs:

- A product with a trusted CI, such as Unfold, fits neither the app nor the library profile.
- `profile-site` was byte-identical to `profile-app`, and `profile-image-set` was
  `profile-library` plus `docker-arg-pins`: two names that only restated a gate and a capability.
- GitOps repositories have no profile.
- `golang.json` and `gitops.json` set their own `groupName`, so their effect depended on their
  position in a repository's `extends` list. After a profile, the `golang.org/x` group held; after
  `automerge-non-major`, the documented order and the one webgrip/ploeg uses, the group was
  overridden and never took effect. A group is also all-or-nothing:
  `config.automerge = config.upgrades.every(u => u.automerge)` in Renovate's
  `workers/repository/updates/generate.js` merges a group only when every update in it merges
  itself, so a group an overlay adds can silently hold updates another part meant to automerge.

## Decision Drivers

- One `extends` line per repository must stay possible, and every published preset name must keep
  working.
- Risk belongs to the dependency: a linter bump is as harmless in an app as in a library, and a
  token library is as sensitive in a library as in an app.
- An overlay must mean the same wherever it sits in an `extends` list.
- Behaviour changes must be visible in review: `docs/policy.md` is generated from the presets and
  its diff is the behaviour change.

## Considered Options

1. Keep one profile per kind of repository, and add more (a product profile, a GitOps profile).
2. Two gate presets, a risk-tier part both gates carry, and capability overlays that only teach
   detection; the old profile names become generated aliases.
3. No shared policy: each repository writes its own `packageRules`.

## Decision Outcome

Chosen option: **2**, because it answers each question once, in the layer that owns it, and keeps
every existing name working.

### Gates

| Gate | A third-party minor, patch or pin update | For |
| --- | --- | --- |
| `reviewed` | waits in one grouped pull request a person merges | repositories that ship what merges: services, products, sites |
| `unattended` | merges itself on green in one grouped branch | repositories whose consumers take each release through their own pull request: packages, presets, reusable workflows, actions, image sets |

Both are generated by `scripts/presets.mjs` from the same parts; the gate part
(`parts/digests-and-actions.json` or `parts/automerge.json`) is the only difference. The names say
who is in the loop for the bulk of updates, which is the question a repository owner answers. They
avoid `app` and `library`, which named kinds of repositories and are what left a product with a
trusted CI without a fit. `manual` and `auto` were considered and rejected: both gates automerge
something and both keep a tick for majors.

### Risk tiers

`parts/risk-tiers.json`, after the gate part and before security fixes, Webgrip's own packages and
the preset bump:

- **Never ships.** npm `devDependencies`, Composer `require-dev`, and `@types/*` in any dependency
  list. Matched by `depType`, which Renovate's npm and Composer managers set, so linters,
  formatters and test runners are covered where they are installed rather than by a package list.
  Minor, patch and pin updates share a `development dependencies` branch that merges itself on
  green after the soak of their update type, under either gate. Renovate's own `packages:linters`
  and `packages:test` lists were considered and not used: they change with the Renovate version
  that runs, not with the tag a consumer pins.
- **Always review.** A short package list: `jsonwebtoken`, `jose`, `openid-client`, `pg`,
  `github.com/golang-jwt/jwt`, `github.com/coreos/go-oidc`, `github.com/jackc/pgx` and
  `github.com/lib/pq`. Minor, patch and digest updates wait for a dashboard tick in a branch of
  their own, without a soak, under either gate. The rule excludes `devDependencies` and
  `require-dev`, so a driver used only by tests ships nothing and stays in the never-ships tier.
  It starts with what Webgrip code uses today (webgrip/ploeg links golang-jwt, pgx and lib/pq) and
  is the owner's to set: see the open questions.
- Everything else: the gate decides.

Majors keep the tick. Security fixes keep their `vulnerabilityAlerts` behaviour, which Renovate
applies on top of every package rule. Webgrip's own packages (`parts/first-party.json`) and the
preset bump (`parts/preset-bump.json`, always last) come later and win.

### Capabilities

`apm.json`, `docker-arg-pins.json` and `golang.json` teach detection only. They set none of
`groupName`, `groupSlug`, `automerge`, `dependencyDashboardApproval`, `minimumReleaseAge` or
`rebaseWhen`, anywhere in the file, and a test fails when one does. The groups they used to set
moved into the policy layer:

- `parts/go-module-groups.json`: the `golang.org/x` and indirect-module groups, carried by
  `default` and both gates at the position the golang overlay used to reach after a profile.
- `parts/agent-package-group.json`: a branch per agent package and one for all
  `webgrip/ai-skills` skills, carried by `default`, by the hand-composed overlays as their last
  part, and by both gates after `parts/first-party.json`, so an agent package keeps a branch of
  its own and its post-upgrade install runs with the right tag.

`golang.json` also lost a rule that matched update type `vulnerability`, which Renovate does not
have; Renovate's `vulnerabilityAlerts` defaults already set `groupName: null`.

**`gitops.json` is not a capability overlay yet.** It extends fifteen external
`home-operations/renovate-presets` files and sets two groups of its own (`Flux OCI Helm charts`,
`GitOps container images`). Moving its groups into `default` would group container images for
every repository with Helm values or Kubernetes manifests, GitOps or not, and the external presets
cannot be checked for policy keys from a self-contained generated file without inlining them, which
loses their order. GitOps repositories keep `default` plus `gitops`; a GitOps gate is a follow-up.

### Aliases

The old names are generated from the gates and stay published:

| Name | Is |
| --- | --- |
| `profile-app`, `profile-site` | `reviewed` |
| `profile-library` | `unattended` |
| `profile-image-set` | `unattended` + `docker-arg-pins` |

Only their `description` differs from the gate, and a test checks each alias equals its gate merged
with its capability overlays. Removing a name is a breaking change for its consumers and would need
a major release; none is planned.

### Consequences

- Good: `reviewed` repositories stop waiting on a person for devDependency and `@types` bumps.
- Good: `unattended` repositories keep a person on the always-review list.
- Good: a Go repository gets the same groups whether `golang` comes before or after the policy
  preset, or is absent; a repository on a gate can add `golang` anywhere.
- Good: a product with a trusted CI can take `unattended` and still keep a person on its
  credential and database libraries.
- Bad: under `unattended`, never-ships updates move out of the one grouped branch into a second
  one, at most one more branch and CI run per Renovate run.
- Bad: a build tool in `devDependencies` (a bundler or compiler) shapes what a site or a bundled
  service ships, and now merges itself on green under `reviewed`. CI builds the artefact, so a
  broken build still fails, but a subtle output change would not.
- Bad: the always-review rule's `depType` exclusion only matches dependencies whose manager sets a
  `depType`; npm, Composer and Go modules do.
- Neutral: Go repositories on `default` or a profile without the `golang` overlay now get the
  `golang.org/x` group too. Hand-composed stacks that put `apm` or `golang` after a non-major
  overlay now resolve as the documented order always did.

### Confirmation

`npm test` resolves every gate and alias with Renovate's own code and checks the policy table in
`scripts/presets.test.mjs`, including each risk-tier case; it fails when a capability overlay sets
a policy key, when an alias drifts from its gate, or when a generated file or `docs/policy.md` is
out of date.

## Open Questions

1. **The always-review list.** Which packages belong on it is the owner's decision. Candidates left
   out of the starting list on purpose:
   - Runtime base images, the last `FROM` of a Dockerfile (Renovate's dockerfile manager gives it
     `depType: final`). Under `unattended` this would put every base image bump of an image set
     behind a tick, which reverses what that profile is for.
   - `golang.org/x/crypto` and `golang.org/x/oauth2`: taking them out of the `golang.org/x` group
     splits modules that release in lockstep and share `go.sum` entries.
   - Password hashing (`bcrypt`, `argon2`), other database drivers (`mysql2`, `go-sql-driver/mysql`)
     and PHP or Laravel auth packages: not found in Webgrip code today.
2. **The npm soak.** npm minors soak 3 days and patches 1 day, as every other datasource. Should
   npm, where compromised releases are usually published and pulled within days, soak longer, and
   should never-ships updates soak at all now that no person reviews them?
3. **Build tools in devDependencies.** Keep them in the never-ships tier (the trade-off above), or
   carve out bundlers and compilers by name?
4. **Commit type for never-ships updates.** They land as `fix(deps)` and cut a patch release,
   though nothing shipped changes. `chore(deps)` also releases a patch here; a type that releases
   nothing would need a `semantic-release-config` rule.
5. **Which gate Unfold takes.** With the always-review list, `unattended` may fit a product whose
   CI is trusted.
6. **A GitOps gate.** What `default` + `gitops` repositories would gain from one, and whether the
   external `home-operations` presets can be inlined or pinned without losing their order.
